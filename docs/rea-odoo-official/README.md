## Method and honest scope

This is **source analysis, not binary reverse engineering.** Odoo ships as
readable Python, XML, and JavaScript; the REA skill explicitly routes complete
source trees to ordinary repository tooling rather than decompilers or runtime
instrumentation. What was kept from the REA protocol is its evidence
discipline: staged phases, every conclusion tied to a cited file and line, and
observations held separate from inferences and unknowns.

Extraction used Python's `ast` module (not regex) for all model, field,
relation, and decorator facts, so the structural counts are exact rather than
approximate.

All indexes are regenerated by `python3 -I build_indexes.py` followed by
`python3 -I gen_tables.py`. Re-running them reproduced every figure in these
documents exactly, with one correction noted below.

Both scripts are checked in under [scripts/](scripts/) and are reproducible
against any Odoo tree by changing the `ADDONS` constant at the top of
`build_indexes.py`:

```bash
cd docs/rea-odoo-official/scripts
python3 -I build_indexes.py   # writes 5 JSON indexes next to the scripts
python3 -I gen_tables.py      # regenerates 06-reference-tables.md
```

`build_indexes.py` reads nothing but the addons tree and writes nothing but
JSON; `gen_tables.py` overwrites only `06-reference-tables.md`.

### Coverage limitations (read before citing these documents)

1. **Enterprise addons are not present.** The requested scope named
   `account_accountant`, `hr_payroll`, `industry_fsm`, and `helpdesk`; all four
   are absent from this Community install. Those domains are **unanalyzed**, not
   analyzed-and-empty. Verified by directory probe.
2. **Static only.** Nothing here observed execution. State transitions are read
   from code and selection definitions; no workflow was run against a database.
   Claims about runtime ordering are inferences from call sites.
3. **`installable: False`.** `iot_drivers` is marked non-installable and is
   indexed but excluded from behavioral conclusions.
4. **Test scaffolding included in totals.** 19 modules are category
   `Hidden/Tests` and contribute models prefixed `test_`/`test.`. Domain
   documents exclude them; global counts do not.
5. **Dynamic model extension is undercounted by design.** Models assembled at
   runtime (`_inherit` resolved through the registry, `base.automation` rules,
   studio-style customizations) are not visible to static AST extraction.

## Headline findings

Four structural facts that a reader coming from an older Odoo should know
first. Each is cited in the linked document.

1. **Security was unified.** `ir.model.access` (CSV) and `ir.rule` (XML) are
   **gone**. Odoo 20 has a single `ir.access` model carrying both an
   `operation` and an optional `domain`; zero legacy artifacts remain across
   all 693 modules. 2,587 rows, of which 531 carry a domain. See
   [02](02-orm-framework-mechanics.md).
2. **`procurement.group` no longer exists as a model.** Procurement is now an
   in-memory `NamedTuple` (`stock/models/stock_rule.py:31`). See
   [03](03-er-diagrams.md).
3. **`account` is the gravitational center**, not `base`: 157 direct dependents
   against base's 40, and 258 of 693 modules sit in the Accounting category.
   See [01](01-module-architecture-map.md).
4. **Cross-module integration runs on one dynamic dispatch**, not on an event
   bus: `getattr(self.env['stock.rule'], '_run_%s' % action)` at
   `stock/models/stock_rule.py:471`, with `mrp` and `purchase_stock`
   registering handlers by defining methods. See
   [04](04-workflows-sequence.md).

## Correction

An earlier revision of [02](02-orm-framework-mechanics.md) reported **3,086**
`ir.access` rows. That figure was wrong: it came from counting non-empty
physical lines, and 101 rows contain a quoted domain spanning multiple lines.
Parsing the files as CSV gives **2,587** logical rows. The corrected number is
used throughout.
